# Auth & safety findings (suite setup, 2026-08-21)

Recorded here because they overturned assumptions in the original plan
and changed how the suite is built. Keep this file - re-read it before
re-enabling anything it says not to.

## 1. HMAC is not required

The Postman collection ("Saathi (Pre) APIs") sends `x-hmac-meta` /
`x-hmac-signature` on 114 of 121 requests, generated by a pre-request
script whose own comment admits the signing payload is a guess
("adjust if your backend signs body+meta"). Verified live against
`pre-apis.ambak.com`:

- `GET /hmac-token` requires `Authorization: Bearer <token>` - it is
  **not** an anonymous secret-issuing endpoint as the collection assumed.
  With a bearer token it returns `{"hmac_token": "<64-hex>"}`, a single
  opaque value, not a shared secret to sign with.
- A bearer token **alone**, with no HMAC headers at all, passed auth on
  every service tried: `finex` (query), `insurance` (query), `payout`
  (query), and a `finex` mutation (`saveRemark`, tested with an
  intentionally invalid variable so it failed GraphQL validation before
  any write executed).

Conclusion: the gateway enforces auth via the bearer JWT only. HMAC
signing is implemented (`src/auth/hmac_signer.py`) but disabled by
default (`SEND_HMAC_HEADERS=0`). Only re-enable it if a specific
endpoint is found that rejects bearer-only auth - and if so, re-verify
the actual signing payload rather than trusting the collection's guess.

## 2. OTP login works with a fixed test account

`mobile=9990511718`, `otp=987789` against `pre` returns a real JWT
(`account/user/validate_otp`, `data.token`). The JWT's `exp` claim is
decades out (~2054) - effectively non-expiring for this test account -
so `src/auth/token_provider.py` caches it to `.cache/otp_token.json`
(gitignored) to avoid tripping the ~15s send_otp cooldown on repeated
local runs.

## 2b. SECURITY: `bank-integration` enforces no authentication at all

Discovered by `tests/negative/test_auth_negative.py`, then independently
reproduced with a bare `requests.post` (no framework, no auth/HMAC
headers of any kind) on 2026-08-21:

```
POST https://pre-apis.ambak.com/bank-integration/api/v1
(no Authorization header, no HMAC headers)
->
200 {"data":{"indiashelter_getSavedData":{"lead_id":2125209,"data":{
  "opts":{"City":"Noida","Pincode":"201301","LastName":"GULATI",
  "FirstName":"TUSHAR","Purpose_of_Loan_P":"Home Construction",
  "Monthly_Family_Income":"1234565",
  "Loan_amount_Required_Cust":"1000000"}, ...
```

Checked across three of its operations (`indiashelter_getSavedData`,
`indiashelter_timeline_steps`, `getBankIntegrationFieldsV2`) - all
returned real data with zero auth. This looks like every read on this
service skips the auth gate entirely (every other service tested -
finex, insurance, payout - correctly 401s without a token). Given
`lead_id`s are small sequential integers, this is plausibly enumerable.

**This should be reported to the backend team.** It is tracked as its
own `xfail(strict=True)` in `tests/negative/test_auth_negative.py`
(separate from the routine `known_bug` bucket below) specifically so it
stays visible and isn't mistaken for an ordinary flaky-data issue. Its
mutations (`SelectPropertyType`, `indiashelter_createLead`,
`indiashelter_saveData`) were NOT tested unauthenticated - doing so
risks a real unauthenticated write - but given the read-side pattern,
treat the possibility that they're also unauthenticated as likely until
the backend team confirms otherwise.

## 3. Incident: three real side effects during suite verification

While building the first version of the REST/GraphQL replay sweeps, the
following **real, external actions were fired against `pre`** on
2026-08-21, all as a direct result of unsafe default classification -
not because the operations were deliberately tested:

| Operation | What happened | Why the guard missed it |
|---|---|---|
| `partner/partner/send_e2e_whatsapp_communication` (REST) | A real WhatsApp message was sent to `8986346939` (template `team_member_invitation`, "sub partner created") | Name-based blocklist (`save/create/update/validate/send_otp/upload`) didn't include "send"/"whatsapp" |
| `finex/api/emailcomms/sendEmailApp` (REST) | An email was almost certainly sent (`to: yt@icicibank.com`, `cc: 90034918@icicibank.com, mhtrivedi2000@gmail.com`) | Same blocklist gap |
| `finex.send_transunion_sms` (GraphQL, declared as a **query**, not a mutation) | An SMS was almost certainly sent to `9629874592` | The generated-query sweep trusted the backend's `query`/`mutation` label as a safety signal; this operation is action-shaped but labeled `query` |
| `bank-integration.SelectPropertyType` (GraphQL mutation) sent with `leadId: 0` | Attempted write with an almost-certainly-invalid lead id | `bank-integration` speaks GraphQL over `/api/v1` with no `graphql` in the URL, so the importer's URL-substring check filed it as an opaque REST body instead of a recognized mutation - it slipped past the mutation gate entirely. Very likely rejected server-side given `leadId: 0`, but not confirmed. |

**Fixes applied as a result** (all now in place):

1. `tools/import_postman.py` classifies GraphQL by **body shape**
   (`{"query": "..."}`), not by `"graphql" in url`. This correctly moved
   `bank-integration` and `reporting-api` traffic into the GraphQL
   operation registry, where `SelectPropertyType` is now properly
   recognized as a mutation and gated behind `ALLOW_MUTATIONS`.
2. `tests/generated/test_endpoints.py` switched from a name-keyword
   **blocklist** to an explicit **allowlist** (`SAFE_READ_POST_NAMES`) -
   every POST endpoint must be individually reviewed and justified
   before it's ever replayed automatically. An assertion at import time
   fails collection if a newly-imported endpoint has no classification.
3. `tests/generated/test_operations.py` no longer trusts `kind == query`
   as a safety signal. Any operation name matching an action-verb
   pattern (`send|notify|create|update|save|sms|email|whatsapp|...`)
   must be explicitly reviewed into `SAFE_QUERY_NAMES` or
   `EXCLUDED_QUERY_NAMES`, with the same import-time assertion.
   `send_transunion_sms` is now permanently excluded.

**If you re-run `tools/import_postman.py` after re-exporting the
collection**, both generated-test files will fail collection on any
newly-discovered action-shaped operation until you classify it - that's
intentional. Read the operation's captured body before adding it to a
safe list.

4. `tests/mutations/test_mutations.py` applies the same default-deny
   discipline to the previously-*always-skipped* mutation sweep. Every
   mutation now needs an entry in `src/testdata/mutation_profiles.py`
   (synthetic data instead of the captured PII, a tier, and a cleanup
   or a documented reason there isn't one), the `ALLOW_MUTATIONS` gate
   is re-checked against the *resolved host* rather than just `ENV`
   (closing a `BASE_URL`-override hole), and reaching a real lender or
   credit bureau needs a second `ALLOW_EXTERNAL_MUTATIONS` opt-in. See
   the "Mutation safety model" section of README.md.
